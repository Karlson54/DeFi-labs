## 2. Запуск

### Крок 0. Підняти локальний блокчейн

У методичці цю роль виконує in-memory мережа Hardhat. Для C#-клієнта потрібна нода
з HTTP-RPC. Будь-який з варіантів:

| Варіант | Команда | Потрібен Node.js |
|---|---|---|
| **Anvil** (Foundry, один бінарник) | `anvil` | ні |
| Hardhat node | `npx hardhat node` | так |
| Ganache | `ganache` | так |

Нода надрукує список тестових акаунтів і їхні приватні ключі та адресу RPC
(зазвичай `http://127.0.0.1:8545`, chainId `31337`).

### Крок 1. Компіляція контрактів

Rider і .NET **не вміють** компілювати Solidity — потрібен компілятор `solc`.
Найпростіший шлях без Node.js:

1. Відкрити https://remix.ethereum.org
2. Створити файли `AssetToken.sol` і `DexPool.sol`, вставити код з теки `contracts/`.
   Remix сам підтягне імпорти `@openzeppelin/contracts/...` з npm.
3. Вкладка **Solidity Compiler** → компілятор `0.8.24+` → **Compile**.
4. Внизу **Compilation Details**:
   - **ABI** → скопіювати масив у поле `"abi"` файлу `contracts/artifacts/<Ім'я>.json`;
   - **BYTECODE** → скопіювати значення ключа `"object"` у поле `"bytecode"` (з префіксом `0x`).

Альтернативи: `solc --combined-json abi,bin` локально або `npx hardhat build`
(тоді artifacts беруться з `artifacts/contracts/*.sol/*.json` — там ті самі ключі `abi` і `bytecode`).

### Крок 2. Конфігурація

У `appsettings.json` заміни плейсхолдер:

```json
"PrivateKey": "ВАШ_ПРИВАТНИЙ_КЛЮЧ"
```

на приватний ключ **тестового** акаунта, який надрукувала нода.

> ⚠️ Ключі локальної ноди публічні й відомі всім — використовувати їх можна ВИКЛЮЧНО
> в локальній мережі.

Опційно: `SimulationSettings:PartnerAddress` — адреса одногрупника, якому буде
надіслано 5000 токенів (порожнє значення = крок пропускається).

### Крок 3. Запуск

```bash
dotnet restore
dotnet run
```

Перший запуск розгортає два токени й пул, вносить ліквідність 1000 : 2000 (курс 1:2)
і виконує обмін 50 токенів A. Адреси контрактів зберігаються у `deployment-state.json`,
тому повторний `dotnet run` не платить газ повторно — він підхоплює вже розгорнуті контракти.
Щоб почати з чистого аркуша — видали цей файл (і перезапусти ноду).

### Очікуваний результат обміну

Резерви 1000 A / 2000 B, обмін 50 A. Угода = 5% резерву → динамічна комісія **1.00%**:

```
Δy = 2000 × (50 × 9900) / (1000 × 10000 + 50 × 9900) ≈ 94.3306 B
```

Спот-курс до угоди — 2.0, ефективний — ≈1.8866, проковзування ≈5.67%.
Для порівняння, зі статичною комісією 0.3% вихід був би ≈94.9660 B — різниця
і є ефектом модифікованої математичної моделі.

## 3. Solidity в Rider + Nethereum: як це працює

**Коротко:** `Nethereum.Web3` — це не компілятор Solidity, а Ethereum-клієнт.
Він робить дві речі: (1) кодує/декодує виклики за ABI, (2) підписує й надсилає
транзакції через JSON-RPC. Сам `.sol` перетворює на байткод окремий компілятор `solc`.

- **Підсвітка `.sol` у Rider:** Settings → Plugins → Marketplace → плагін **Solidity**.
  Він дає підсвітку синтаксису й навігацію, але не компілює контракти в артефакти для .NET.
- **Пакет:** `dotnet add package Nethereum.Web3` (або NuGet-вікно Rider). Він тягне за собою
  `Nethereum.Contracts`, `Nethereum.ABI`, `Nethereum.JsonRpc.Client`.

## 4. Чому саме такі рішення в коді

**Шарувата архітектура замість одного скрипта.** `Program.cs` не містить бізнес-логіки —
лише збірку конфігурації, реєстрацію DI та вивід. Уся робота з мережею інкапсульована
в сервісах, кожен з яких відповідає за одну зону: токени, пул, артефакти, стан, звіт.

**Інтерфейс + реалізація для кожного сервісу.** Навіть за однієї реалізації це дає
точку підміни: у юніт-тестах `IDexPoolService` можна замінити на мок і перевірити
логіку сценарію без реальної ноди.

**DI через `ServiceCollection`.** Сервіси отримують залежності конструктором і не створюють
їх усередині методів. Виняток — `Account` у `Web3Factory`: приватний ключ відомий лише
в рантаймі, тому підписувач створюється фабрикою, а не реєструється в контейнері.

**Конфігурація через `appsettings.json` + `IOptions<T>`.** Жодного хардкоду RPC-URL, адрес
чи параметрів сценарію. Курс 1:2 і обсяг обміну 50 — це дані, а не код.

**DTO на кожен крок.** Наверх не витікають типи Nethereum (`TransactionReceipt`, `HexBigInteger`):
сервіси повертають `SwapResult`, `PoolStateSnapshot` тощо, вже переведені з wei у звичайні числа.
`record` — бо ці об'єкти немутабельні за задумом.

**Персистентність розгортання.** `deployment-state.json` зберігає адреси контрактів.
Розгортання — дорога операція, тому повторювати
її при кожному запуску немає сенсу.

**Async/await скрізь.** Кожен виклик до ноди — мережевий IO, синхронне очікування
блокувало б потік. `Task.WaitAsync(timeout)` захищає від зависання на мертвій ноді.

**Обробка помилок.** У `Program.cs` окремо перехоплюються нема-з'єднання, відмова RPC,
таймаут і помилки конфігурації — з поясненням, що робити, а не голим стектрейсом.
