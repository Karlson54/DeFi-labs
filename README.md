# Лабораторна робота №4 — Композитність: інтеграція з Uniswap V2 Router

**Тема.** Інтеграція смарт-контрактів з існуючими протоколами децентралізованого
обміну на рівні програмних інтерфейсів (Composability).

Клієнт — консольний застосунок C# (.NET 8) + Nethereum, повністю самодостатній:
сам випускає два власні ERC-20 токени, сам розгортає контракт-посередник
`DefiIntegrator` і через нього викликає **чужий** Router-контракт (Uniswap V2
або сумісний форк) для створення пулу ліквідності та обміну.

## Запуск

### Крок 0. Тестова мережа з розгорнутим Uniswap V2

Найпростіше — публічний форк Uniswap V2 у Sepolia (адреса Router-а видається
викладачем/береться з документації обраного форку). Альтернатива — локальний
Hardhat-форк мережі, де Uniswap V2 вже задеплоєний.

### Крок 1. Компіляція контрактів

1. https://remix.ethereum.org → створити `AssetToken.sol`, `DefiIntegrator.sol`
   та `interfaces/IUniswapV2Router02.sol`, вставити код з теки `contracts/`.
2. Solidity Compiler → `0.8.24+` → Compile.
3. З Compilation Details скопіювати `ABI` та `BYTECODE` у відповідні файли
   `contracts/artifacts/AssetToken.json` і `DefiIntegrator.json`.

### Крок 2. Конфігурація

Скопіювати `appsettings.example.json` → `appsettings.json`, заповнити:

- `Web3Settings:RpcUrl`, `ChainId`, `PrivateKey` — тестовий гаманець з ETH
  у Sepolia (або дані локальної ноди);
- `Lab4Settings:RouterAddress` — адреса Router-контракту обраного DEX.

### Крок 3. Запуск

```bash
dotnet restore
dotnet run
```

Перший запуск: емітує два токени, розгортає `DefiIntegrator`, надає йому
approve, викликає `provideLiquidity` (створення пулу у **зовнішньому**
протоколі) і `swapTokens` (обмін через щойно створений пул). Адреси
зберігаються в `deployment-state.json` — повторний запуск не платить газ
за деплой повторно.

## Контрольні запитання

**Factory vs Router — у чому різниця, з ким взаємодіють користувачі?**
`Factory` створює нові пари-пули й веде їхній реєстр; сам пул (`Pair`)
максимально спрощений заради економії газу і не має захисту від slippage чи
зручних multi-hop обмінів. `Router` — обгортка над Factory/Pair: рахує
математику, перевіряє мінімальні суми виходу, підтримує маршрут через кілька
пулів. Кінцеві користувачі (і контракти на кшталт `DefiIntegrator`)
взаємодіють саме з `Router`.

**amountOutMin / amountAMin, amountBMin — від чого захищають?**
Від проковзування ціни (slippage) між підписом транзакції і її виконанням у
блоці, зокрема від MEV-атак (фронтраннінг/сендвіч-атаки): якщо результат
гірший за задане мінімальне значення — транзакція відкочується (Revert),
кошти користувача не втрачаються на невигідному курсі.

**Чому інтегратор сам викликає approve для Router-а, хоча користувач вже дав
approve інтегратору?**
`approve` — дозвіл конкретного власника токенів конкретному `spender`-у.
Approve користувача до `DefiIntegrator` дозволяє лише інтегратору забрати
токени на свій баланс. Після цього власником (з точки зору ERC-20) є вже сам
контракт, і щоб Router зміг їх списати для `addLiquidity`/`swap`, потрібен
окремий approve — цього разу від `DefiIntegrator` до `Router`.

**Навіщо в Router-функціях масив `path`, і чому не обмежений двома
елементами?**
Прямого пулу між двома довільними токенами може не існувати. `path` описує
ланцюжок обмінів через проміжні активи з високою ліквідністю (найчастіше —
WETH): `TokenA -> WETH -> TokenC`. Router виконує обмін по цьому маршруту в
одній транзакції, тому елементів може бути більше двох.
